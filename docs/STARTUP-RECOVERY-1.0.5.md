# 1.0.5 自启、快捷键与整应用恢复

旧版只在数据库首次初始化时注册自启，后续移动运行目录不会核对或修复路径；注册项采用通用的 electron.app.Electron 名称。旧版界面仅根据 openAtLogin 判断，未核对 Windows 启动管理器的实际启用状态。指定电脑诊断时，注册表项存在且目标文件存在，但没有 Clipboard 进程运行；这解释了为什么当时 Win+V 由系统窗口接收，尚不能据此确定应用此前退出的具体原因。

新版固定 AppUserModelId 和自启项名称为 ClipboardLocal；按数据库中的显式自启偏好，在正常启动时核对并重写当前路径，未设置偏好时默认开启。开启滑块明确设置 enabled 并检查 executableWillLaunchAtLogin 与启动条目状态；迁移时只删除指向当前可执行文件的旧用户条目。手动关闭的偏好仍被保留。

Win+V 辅助进程退出或心跳中断时自动重启。低级键盘回调中的输出移至消息计时器，避免回调被管道 I/O 阻塞；每 10 秒更新公开用户态键盘钩子，以恢复被 Windows 静默移除的钩子。没有驱动或内核修改。新增不含剪贴板内容的启动与退出诊断日志，写到本机应用数据目录 runtime.log。

8 项自动测试通过。完整 Windows 包运行验证：https://github.com/trlstdin/rororororo/actions/runs/40183198185 ，实际环境 Windows Server 2022。指定 Acer 电脑通过旧分支 5.4 的客户端连接，主机指纹与本次用户提供凭据一致，hostname 为 LAPTOP-MCMQHDN4。该电脑实际为 Windows 11 build 26200，不是 Windows 10 实机。

验证不包含整机重启或注销。自启验收已核对实际注册命令、实际启用状态，并以相同 --background 参数通过用户交互会话启动，随后验证真实 Win+V。

Windows 新增独立恢复守护，使用当前用户任务计划程序启动，监视运行中的主进程。主进程或整个进程树意外结束后，由独立守护启动新的用户交互任务恢复应用。托盘“退出”先写入本次实例的停止标记，守护停止，不会重新拉起。本次退出不会修改用户的开机自启偏好；下次登录仍按开关设置执行。关机/注销时不在结束中的会话强行重启。Linux 本次没有新增整应用守护。

测试专用 trayQuit 调用与托盘菜单共享同一个退出函数。恢复测试使用独立配置，结束进程树不会影响原有历史数据库。

指定 Acer 实机的最终专项验收 8 项通过，记录见 recovery-1.0.5-result.json：独立守护就绪，跨过多次钩子更新后实际 Win+V 唤出；主动结束完整进程树后 PID 从 4632 变为 36288；恢复后实际 Win+V 有效；托盘退出后应用和守护都退出且未重启；按注册表原始 --background 参数启动正常配置，实际 Win+V 唤出且自启注册保持启用。

最终正常实例 PID 33012，会话 1，窗口句柄 11863316；独立守护 PID 29592，存活状态已核对。原数据库保留，最终历史记录 14 条，快捷键为 Super+V。没有上传历史内容，截图来自合成数据的独立验证配置。以上 PID 等是验收时观测值。

验证过程中发现定期更换钩子的顺序问题，改为先卸旧钩子再安装新钩子，并增加跨越更新周期后的实际按键验证。Windows 验证产物上传曾遇到 Actions 存储配额限制，源码/包推送不受影响；证据保存增加 Filebin 备用路径，最终 Windows 工作流通过。
