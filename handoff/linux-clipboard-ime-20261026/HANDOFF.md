## 目标环境和位置

- Windows 宿主机上的 VirtualBox 虚拟机：`Ubuntu-24.04-Version-C`。
- Linux：Ubuntu 24.04.4 LTS，登录用户 `versiona`，会话曾确认为 GNOME X11、`DISPLAY=:0`。
- 剪贴板项目：`/home/versiona/xxm/clipboard`。
- Linux 运行包：`release/clipboard-linux-x64`，应用版本 1.0.5。
- 剪贴板数据：`dev/profile/history.sqlite`，须保留用户历史。本目录没有收录数据库或历史内容。
- 输入法安装记录和缓存：`/home/versiona/xxm/chinese-input`；实际已切换到系统原生安装的 `/usr/libexec/ibus-engine-libpinyin`。

目录中的脚本保留目标机实际路径，不能直接当作适用于其他电脑的通用安装脚本。

## 剪贴板修改经过及当前意图

1. 完整 Linux 包由虚拟机从仓库授权直链自行下载并解压。未将第三方下载地址、配对码或用户密钥写入本目录。
2. 建立 `~/.local/bin/clipboard-local` 包装入口，显式指定 X11、禁用 `GlobalShortcutsPortal`，并使用独立数据目录。
3. 建立过登录自启和应用菜单入口；为默认用户数据目录建立过指向 `dev/profile` 的链接。当前链接和值见 JSON 快照。
4. 多次尝试过“应用自身快捷键”和“GNOME 自定义快捷键调用启动器”两种方式，不能把中途配置混作同一个最终方案。
5. 最后一次配置意图是：应用自身保存 `Super+V`；撤掉 GNOME 自定义的 `clipboard-local/` 快捷键条目，避免两个入口争用。实际导出值见快照。
6. GNOME 通知托盘改为 Win+M；搜索概览改为 Win+S；关闭单独 Win 键触发概览搜索的设置。这些配置值不等于用户实体按键已验证。
7. 早期重启脚本用 `/proc/PID/cmdline` 的第一个 NUL 分隔段与可执行文件路径精确比较。但 Electron 的该段包含整条命令，导致旧进程 15684 没被匹配。后续才真正退出旧进程，并启动过 24006、24517。**这些 PID 只是事故记录，后续操作必须重新识别，不能照抄杀进程。**

自启文件可能被应用启动时重新生成，其参数与包装脚本并不一致；尤其不能假设禁用 portal、数据目录等参数在重新登录后完全等价。尚未做重启后验收。

### 宿主机拦截修改

- 发现宿主机原有剪贴板有全局 Win+V 监听，曾观察到宿主机剪贴板窗口出现。
- 修改过监听器，使目标 Ubuntu 虚拟机获得焦点时让事件继续向后传递；增加过 Win 键按下时记录目标的逻辑。
- 曾错误加入调用 VirtualBox 扫描码发送的转发。**该新增转发已经撤销，随后从正在运行的监听进程中核验 `scan_injection=False`。不可重新引入。**
- 原上游 Windows 监听器本来就有用 `keybd_event` 屏蔽开始菜单的代码。当前快照如实保留该原有部分，不能据此声称“整个程序完全没有合成按键”。它不应被拿来做实体键盘验收。
- 仅把 VirtualBox 的键盘自动捕获配置改为 true，不能证明任一时刻的实际捕获状态。默认宿主键曾显示为 Right Ctrl，需检查它与用户按键的关系，不能未采集事件就断言根因。
- Windows 源码备份位于 `I:\xxm\beifen\clipboard`，相关文件名见快照；未将这些历史 ZIP 或已撤销的注入代码再次发布。

## 输入法修改经过及当前意图

1. 先下载并尝试过用户目录解包、proot 运行引擎。这条路径曾注册出带 `-debug` 的引擎，不作为交付方案。
2. 后来已原生安装 `ibus-libpinyin`。用户目录的临时引擎启动器、自定义组件和自启项已清理过；安装缓存目录可能仍有残留，不应误认为实际运行入口。
3. 输入源配置为 `libpinyin` 和美式键盘，值见快照。
4. GNOME 原生输入源切换器会显示选择界面；用户明确拒绝这种交互。因此将它的前向、后向快捷键清空，另将 Ctrl+空格绑定到 `toggle-chinese-input`。
5. 当前脚本读取 `ibus engine`，在 `libpinyin` 与 `xkb:us::eng` 之间切换；使用 `flock` 防止并发，并读取实际 engine 判断结果。**单次命令返回码、脚本成功日志、全局 engine 名称均不能单独证明实际输入框已切换。**
6. `flock` 只防并发，不保证一次实体按压只触发一次。已有同一秒内往返切换的日志，需核对是否重复触发或用户多次按压；目前不能断言是哪一种。
7. 原生安装后曾替换运行中的 IBus daemon。已有应用的输入法连接、输入上下文与全局 engine 是否一致，仍需核对。

只读观察曾发现：GNOME 和媒体键守护进程使用同一用户会话总线；选取的实际 OpenBrowser/Chrome 进程没有显示所查的输入法环境变量；`gtk-im-module` 设置为空。上述是观察，不是已证明的故障根因。

## 必须作废的验收结论

- XTest 注入、Windows `keybd_event`、VirtualBox `keyboardputscancode` 都不是实体键盘验收。
- 强制设置焦点、先发送 Escape 清除界面、创建一个显式配置 IBus 的 GTK 输入框，会改变用户现场，不能证明用户原应用中快捷键有效。
- 直接执行 `ibus engine` 只证明后端可被调用，不能证明键盘快捷键、应用输入上下文和文本提交整条链路正常。
- 早期截图和检查混入宿主机剪贴板窗口。必须识别 Linux 窗口的进程归属，且仍不能用“窗口出现”反推它一定由实体快捷键触发。
- 截图包含用户剪贴板中的敏感内容，本目录不收录这些截图，也不收录用户历史、私钥、配对码或临时授权下载链接。
