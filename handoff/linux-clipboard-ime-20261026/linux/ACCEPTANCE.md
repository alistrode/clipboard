## 之前为何产生“测试通过，实际无效”的错误结论

旧交接记录的误判是把局部状态当作用户端完整效果：XTest、keybd_event 或 VirtualBox 扫描码注入替代实体键盘；直接运行启动器或 ibus engine 替代快捷键触发；把宿主机剪贴板窗口当成 Linux 窗口；主动清界面、强制焦点或新建专用 GTK 输入框后，将改变现场的结果推广到用户原应用。成功日志、返回码和保存过配置都只证明对应局部操作。

这些证据不支持“用户实体快捷键已修复”。不得继续引用旧的通过表述，不得为了通过验收恢复已撤销的按键转发。

## 后续 AI 必须执行的验收规则

1. **禁止按键注入**：不得使用 XTest、xdotool key、keybd_event、SendInput、VirtualBox keyboardputscancode 等发送按键，也不得用这些结果替代实体按键。此处不附带可执行的注入脚本。
2. 先记录目标：Windows 宿主机还是 Linux 来宾、实际应用与输入框、当前焦点和捕获状态。不得靠改变焦点、清界面或替换测试应用制造通过。
3. 诊断按层区分：实体设备 → 宿主机拦截 → VirtualBox 捕获 → Linux 原始事件 → GNOME/应用快捷键回调 → 窗口或实际应用输入上下文。只读定位先于修复；缺少的层明确写“未采集”。
4. 按键记录仅限这两组快捷键的必要事件、来源、左右修饰键与时间，区分实体/合成；不采集普通输入内容、剪贴板历史或无关窗口。
5. Win+V 通过证据须来自用户实体操作及 Linux 目标窗口，确认进程归属；宿主机窗口不计入。窗口直接启动仅计作组件检查。
6. Ctrl+空格须在用户原应用输入框验证实际中英文输入和文本提交；全局 ibus engine 名称变化、回调日志或脚本退出 0 均不足以判通过。一次按压往返切换要查事件与回调时间，禁止凭同秒日志推断重复触发原因。
7. 每组快捷键分别报告：实体触发证据、实际结果、未覆盖场景、结论来源。只验证一组不能称两组修复。用户反馈有效与 AI 独立采集完整链路要分开标注。
8. 用户反馈无效立即撤销不受证据支持的通过结论，继续定位。无实体证据写“未验证”，不把“已写配置/已启动/后端可调用”写成“修复成功”。
9. 自启、重登录、重启、不同应用分别验收，未测不外推。不得强迫用户反复配对或重复测试；持续工作每分钟报告实质进度。

## 可直接复用的报告格式
